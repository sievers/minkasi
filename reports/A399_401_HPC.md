# A399-401 joint M2 + ACT needlet map on an HPC: resources handoff

Written 2026-11-11 on `psd` (64 cores, 251 GB), where the run cannot fit. This note is for a new session that has to size and launch
the run on a machine with more memory. It is self-contained; the wider project log is `reports/HANDOFF.md`.

## 1. Goal

One joint map of the A399-401 bridge, MUSTANG-2 TODs plus ACT DR6 f090, made with the current baseline: noise models only, no hits
mask, no prior.

```
python examples/twores_ex.py --name A399_401 --idir <TODs>/ --ntods <304/nranks> --act-glob <ACT>/all_f090_ivar.fits \
    --direct --cg 600 --cg-tol 0 --cg-save 40 100 200 400 600 --lattice-tol 1e-3 --min-hits 0 \
    --cache <cache dir> --outroot <out>/A399_401 [--radius R]
```

Run it under `mpirun -n <nranks>` with `OMP_NUM_THREADS=OPENBLAS_NUM_THREADS=NUMBA_NUM_THREADS=1`. `--ntods` is the number of TODs per
rank: each rank takes the next `--ntods`, so nranks × ntods must cover all 304.

The A401 decrement is at the top of the field. A399 is at the bottom left, outside the M2 coverage.

## 3. Memory model (measured; the important part)

**Every MPI rank holds a full copy of all the M2 response matrices.** These are the probed diagonal needlet blocks used by the
preconditioner. They dominate memory.

- **Size depends only on the map lattice and the probe window**, not on the hits or the number of TODs. Each band stores
  (lattice points) × (window entries per row).
- **Window.** The window is the full lattice if the band has ≤ 5000 points (`--exact-below`). Otherwise it is
  (2⌈r/downsamp⌉+1)², with r = min(`--radius`, 2 × filter extent).
- **Map size.** The map is sized from the TODs' extent plus 25% padding (`--pad-frac`). A399-401 is 1260 × 1260 pixels of 3″, against
  480 × 480 for MOOJ1142.
- **A smoke test on a few TODs measures a smaller map.** It does not tell you the memory of the full run. That is what went wrong
  here: a 4-TOD smoke test got a 480² map and reported 13.5 GB per rank, and the real run was then OOM-killed at 32 GB per rank and
  still growing.

**`--dry-run` gives the numbers without probing.** It reads the TODs, prints each band's lattice and window, and prints the memory per
rank, then exits. It takes a few minutes. Use the same TOD set and options as the real run, because the lattice depends on the
TODs' extent. The rank count doesn't matter.

- **Calibration on MOOJ1142 (106 TODs).** The dry run reproduces the cached matrices exactly, band by band. It predicts a 12.0 GB
  peak plus the TODs, against a measured ~13 GB per rank.
- **Peak** is while probing the largest band (band 7): about 54 bytes per entry of that band, plus the bands already stored.
- **Resident** is the stored CSR matrices, 12 bytes per entry, or 16 for a band with more than 2³¹ entries. They stay in memory through
  the CG.
- **TODs** add about 3 GB per rank at 38 TODs per rank, and scale with TODs per rank.

A399-401 dry runs (304 TODs, `--lattice-tol 1e-3`):

| `--radius` (pixels) | entries | band 7 window | resident / rank | peak / rank (probe) + TODs | response cache on disk |
|---|---|---|---|---|---|
| 30 (default) | 3.20 G | 39×39 | 48 GB | ~140 GB (+10% margin: >2³¹ entries in band 7) + ~3 GB | ~25 GB |
| 14 | 2.06 G | 29×29 | 25 GB | ~81 GB + ~3 GB | ~16 GB |
| 6 | 0.67 G | 13×13 | 8 GB | ~19 GB + ~3 GB | ~5 GB |

Lattices: downsamps [315 140 63 30 12 6 3 1 1 1]. Points per side: [4 9 20 42 105 210 420 1260 1260 1260].

**`--radius` changes only the preconditioner, not the answer.** The CG applies the exact TOD operator (`todvec.dot`) every iteration,
and the matrices are used only in the block preconditioner. A smaller window may need more CG iterations. On MOOJ1142, radius 30 and
radius 14 differ only in bands 5–6, since bands 7–9 are already narrower than 14 there. Radius 6 is untested. If you use it, compare
the CG residual curve against radius 14 on MOOJ1142, or judge by the A399-401 saves at 100/200/400/600.

Other memory, smaller than the probe peak:

- **Block-solver setup** makes one shifted copy of each large band, plus its row slice split over ranks. At radius 30 that is about
  48 + 39 GB + slice. Below the probe peak, but close.
- **ACT responses** cover only bands 0–3 and are small. CG vectors are about 130 MB each.

## 4. Time model (measured on psd, 8 ranks × 38 TODs, 1 thread per rank)

| stage | measured / estimated | scales with |
|---|---|---|
| read TODs, noise models | ~10 min | TODs per rank |
| initial PCG (`--maxiter 50`) | 97 s/iteration → 81 min | TODs per rank × map pixels (per-TOD needlet transforms) |
| probing | ~1.4 s per probe apply; applies per band = window entries (lattice points for exact bands): r=30 4835 → ~1.9 h, r=14 3739 → ~1.5 h, r=6 2723 → ~1.1 h | TODs per rank |
| smallest eigenvalue of each large band (eigsh, cached in `<cache>_lmin.json`) | minutes on MOOJ1142; not measured here, could be ~1 h at r=30 | matrix entries |
| CG | ~100 s/iteration for the TOD operator + preconditioner (20 Jacobi inner iterations on bands 5–9, rows split over ranks; ~20–40 s at 8 ranks, r=30) → ~2 min/iteration, **600 iterations ≈ 20+ h at 8 ranks** | TOD part: TODs per rank; preconditioner: entries / ranks |

The CG time is dominated by the TOD operator. It is the same operator as the initial PCG, and it costs ∝ (TODs per rank) × (map
pixels), because the needlet transforms are redone for every TOD. For MOOJ1142, 7 TODs per rank on 480² gave 2.6 s per PCG iteration
and 4.7 s per CG iteration. Scaling by 38/7 × (1260/480)² ≈ 37 matches the 97 s measured here.

**Consequence: time wants more ranks, but every rank costs the full matrix memory.**

| setup | memory | estimated wall clock |
|---|---|---|
| 32 ranks (9–10 TODs each) at r=14 | ~32 × 84 GB ≈ 2.7 TB in total, e.g. 4 nodes × 8 ranks with ≥ 700 GB each | ~6–8 h |
| 8 ranks at r=30 | ~8 × 145 GB ≈ 1.2 TB | ~1 day |

Ranks can span nodes: only maps and vectors are reduced over MPI. Do not put more ranks on a node than its memory ÷ peak per rank
allows. The probe peaks happen on all ranks at the same time.

## 5. Suggested procedure

1. Install, then run `--debug`.
2. Run `--dry-run` with the exact production options, including `--radius`. Confirm the table above on the new system; the lattice
   should be the same. Choose the radius and rank count from node memory: peak per rank ≈ printed peak + ~0.08 GB per TOD on that rank,
   plus ~10% margin.
3. Run a short job with the production rank layout and `--cg 5 --cg-save 5`.
   - This measures the real peak, via Slurm `sacct -o MaxRSS` / `seff`, or the RSS sampler in
     `/mnt/welch/USERS/jorlo/needlets/a399_401/run.sh`.
   - It also measures the time per CG iteration.
   - The probe fills `--cache`, and the full run reuses it, so this is not wasted. **But** `cached_responses` does not record the
     radius, TODs or units in the file name. Use a fresh `--cache` directory per configuration, and never reuse the psd caches.
4. Run the full job with the same `--cache`.
   - Saves `<outroot>_cg<N>.npy` at the `--cg-save` iterations, plus `_final.fits`, `_hits.fits`, `_need.fits` and `_act.fits`.
   - Convergence is judged by the map changing between saves (and by `CG iter N: |r|/|b|` in the log). The residual is over all
     coefficients and is not a map error. On MOOJ1142 it reached ~4e-4 at 600 iterations.
5. Post-processing, from `examples/`. Expect the inner M2 region to be consistent with ACT at order unity in noise units, as on
   MOOJ1142.
   ```
   python act_consistency.py --root <out>/A399_401 --act-glob <ACT>/all_f090_ivar.fits --size 70 --label "A399-401, 304 TODs"
   python multiscale_map.py --joint <out>/A399_401_final.fits --hits <out>/A399_401_hits.fits --act-glob <ACT>/all_f090_ivar.fits \
       --size 70 --smooth 10 --smooth-ref-hits 3000 --show-hits 120 --feather-hits 300 --outline \
       --title "A399-401, M2 + ACT" --out <out>/A399_401_multiscale.png --fits <out>/A399_401_multiscale.fits
   ```

## 6. If memory is still too large: code changes, none done yet

1. **Do not keep the full matrices through the CG.** `JointMapper.m2_resp` and `responses` hold every band on every rank after
   `block_solver` has built its solvers. The large bands only need their row slice. Dropping the full copies after the solver is
   built would cut CG-time residency to about resident ÷ ranks for bands 5–9. Check that nothing later uses them; `--resdiag` and
   `--ritz` might.
2. **Probe once per node and share** through MPI shared memory (`MPI.Win.Allocate_shared`). This divides the matrix memory by the
   ranks per node. It is a bigger change.
3. **Assemble the probed band directly into CSR.** `probe_band` currently builds Python lists of float64 values and int64 row and
   column indices, then concatenates them, masks them, builds a COO and symmetrises it (G + Gᵀ)/2. That makes several full-size
   copies; the peak is ~54 bytes per entry against 12 stored. Preallocating int32 or int64 arrays of the known size would bring the
   peak close to the resident size.
4. **Speed: needlet transforms once per apply instead of once per TOD.** The CG's TOD operator transforms the needlet map for every
   TOD. Transforming once to a real-space map, projecting all TODs, and transforming back once would cut the ~100 s per iteration
   by a large factor. This is the biggest time saving.
5. **Less padding** (`--pad-frac 0.1`) gives about 30% fewer pixels. Edges then sit closer to the data.

## 7. Project conventions (from CLAUDE.md and the user)

- **Baseline is noise-driven only**: no masks (`--min-hits 0`), no manual band cuts, no prior. Q deprojection is removed. No
  scan-synchronous templates.
- **Scripts** take an argparse CLI with `--debug`. Functions belong in minkasi, not in scripts. Run `ruff check` and `ruff format`
  before running code. Use type hints and full docstrings.
- **No WITCH imports inside minkasi.** WITCH only in simulation scripts.
- **Reports** are HTML with figures, kept up to date: `reports/convergence_summary.html` and `reports/needlet_mapmaking.html`.
